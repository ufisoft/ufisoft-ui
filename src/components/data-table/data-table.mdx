# DataTable

A data table for admin screens: sorting, search, column filters, pages, row selection and actions, column management, row reordering and virtualization, on the client or the server.

<Canvas of={DataTableStories.Default} />

## When to use

- Lists of records users scan, sort and page through: users, orders, pages, logs.
- Data that lives on a server and is fetched page by page (`mode="server"`).

## When not to use

- A small, fixed table with no sorting or paging (a pricing comparison, a spec sheet) — use `Table`.
- A list of cards or media — use `Grid`.
- Key–value details of one record — use a description list or `Stack`.

## Props

<ArgTypes of={DataTableStories} />

**Columns.** Each column has an `id`, a `header` and usually a `value` — what it sorts by and what it shows. `cell` renders custom content (a `Badge`, a link, actions); `compare` gives the column its own order. A column with `value` or `compare` is sortable unless `sortable={false}`. Without `cell`, numbers and dates are formatted for `locale`.

**Rows.** `data` is the rows; `getRowId` gives each a stable id (it defaults to the index in `data` — set it when rows can be selected, expanded or removed). `getRowLabel` names a row for its checkbox and buttons (“Select Ayşe Kaya”); it defaults to the row’s first value.

**Client or server.** `mode="client"` (default) sorts and pages `data` itself. `mode="server"` shows `data` as the current page and `totalCount` as the total; every change is reported so your server does the work:

```tsx
const [query, setQuery] = useState<DataTableQuery>({
  sort: [],
  filters: {},
  search: '',
  page: 1,
  pageSize: 25,
});
const { rows, total, isLoading } = useUsers(query); // your fetch

<DataTable
  caption="Users"
  mode="server"
  columns={columns}
  data={rows}
  totalCount={total}
  loading={isLoading}
  globalSearch
  sort={query.sort}
  filters={query.filters}
  search={query.search}
  page={query.page}
  pageSize={query.pageSize}
  onQueryChange={setQuery}
/>;
```

`onQueryChange` receives `{ sort, filters, search, page, pageSize }` after every change — one place to fetch from. The separate callbacks (`onSortChange`, `onFiltersChange`, `onSearchChange`, `onPageChange`, `onPageSizeChange`) also fire.

**Search and filters.** `globalSearch` adds a search field that looks in every column with a `value` (unless `searchable={false}`), ignoring case and accents (“cagla” finds “Çağla”); it applies `searchDebounce` ms (300) after the last keystroke. A column with `filter` gets a filter button in its header; the type decides the editor:

| `filter.type` | Editor                                     | Matches                                               |
| ------------- | ------------------------------------------ | ----------------------------------------------------- |
| `text`        | contains / is / starts with + a value      | the value as text, ignoring case and accents          |
| `number`      | min and max                                | numbers within the bounds (inclusive)                 |
| `select`      | a select, or checkboxes with `multiple`    | any of the chosen `options`; also inside array values |
| `date`        | a `DateRangePicker`                        | whole days from–to (Dates or date strings)            |
| `boolean`     | Any / yes / no (`trueLabel`, `falseLabel`) | the value as true or false                            |

A filter applies on _Apply_ or Enter — a server is asked once, not per keystroke. Active filters are listed above the table; each can be removed, or all at once. `filterValue` filters on something other than `value`, `label` names a column whose header is not plain text, and `dateLocale` (from `react-day-picker/locale`) translates the date filter's calendar. Filters are `{ [columnId]: { type, … } }` — the same shape your server receives.

**Selection.** `selectable` adds a checkbox to each row and a “select all on this page” checkbox to the header (indeterminate when some are selected); `isRowSelectable` disables some rows. Selection survives paging and sorting. It is `{ ids, allMatching }`: when a whole page is selected and more results exist, the bar offers “Select all 245 results”, which sets `allMatching`. In client mode `ids` then lists every matching row; in server mode only the rows seen — act on the query. Clearing one row or changing filters or search ends “all results”. Controlled with `selection` + `onSelectionChange`, or `defaultSelection`.

**Bulk actions.** While rows are selected, a bar above the table shows the count, `bulkActions` and “Clear selection”. An action's `onSelect` receives `{ selection, rows, query, clearSelection }` — `rows` are the selected rows the table has (all of them in client mode, the current page's in server mode).

**Row actions.** `rowActions` adds a “⋯” menu button at the end of each row; the same actions open from the row's context menu (right-click, long-press, or the Menu key / Shift+F10 inside the row). `disabled` turns an action off for some rows, `tone: 'danger'` marks destructive ones.

**Row click and details.** `onRowClick` is called for clicks on a row outside its buttons, links and fields (not while text is selected). `renderDetail` adds a button at each row's start that opens a full-width detail row below it; return `null` for rows without one. Open rows are controlled with `expandedRowIds` + `onExpandedChange`, or `defaultExpandedRowIds`.

**Columns: resize, reorder, hide, pin.** `resizableColumns` adds a handle to each header's end edge: drag it, or focus it and use the arrow keys (Shift for steps of 50 px), Home and End; double-click resets the width. `reorderableColumns` lets headers be dragged within their pinned group. `columnChooser` adds a “Columns” button whose popover shows or hides each column, moves it up or down (the keyboard way to reorder) and pins it to the left or right; “Reset columns” returns to the defaults. Per column: `width` (px; without one the column shares the free space), `minWidth` / `maxWidth` (48 / 1200), `resizable`, `hideable`, and the starting `hidden` and `pinned`.

Resizable or pinned columns switch the table to a fixed layout: set widths hold, long cell text ends in “…”, and columns without a width share the rest (at least 8rem each). Pinned columns stick while the table scrolls sideways; the selection and detail columns pin with the left group, the actions column with the right one. A pinned column without a width keeps the width it had (160 px when pinned from the start).

The column state is `{ order, hidden, widths, pinned }` — controlled with `columnState` + `onColumnStateChange`, or `defaultColumnState`. With `storageKey` (uncontrolled), it is kept in `localStorage` and restored on the next visit, after the first render so server and client agree. Hidden columns keep their filters and sort.

**Reordering rows.** `reorderableRows` adds a drag handle at each row's start. Drag it (mouse, pen or touch; the region scrolls near its edges), or focus it and press Space or Enter to pick the row up, the up and down arrows to move it and Space or Enter to drop it — Escape cancels. The table does not change `data`: `onRowReorder` receives `{ row, rowId, targetRowId, position, fromIndex, toIndex }` with indexes in `data` (in server mode, the page), so you apply the move and save it:

```tsx
onRowReorder={({ fromIndex, toIndex }) =>
  setRows((rows) => {
    const next = [...rows];
    next.splice(toIndex, 0, ...next.splice(fromIndex, 1));
    return next;
  })
}
```

Rows move among the rows shown (this page, these filter results). The handles are off while the table is sorted — the order shown is then not the order of `data`.

**Many rows.** `virtualized` renders only the rows in view (plus `overscan`, 8) inside the `maxHeight` box (`lg` when not set); spacer rows keep the scroll bar honest. Use it with `paginated={false}` for thousands of rows. Row heights start at `estimatedRowHeight` (41, or 33 when compact) and are measured as rows render, so wrapped text and open details work. The columns use the fixed layout, so their widths do not change while scrolling. A focused or dragged row stays rendered when it scrolls away.

**Loading more.** Without paging, `hasMore` with `onLoadMore` adds a “Load more” button, and with `maxHeight` or `virtualized` asks again by itself when the view comes within one screen of the end (once per batch). Set `loading` while fetching and append the rows to `data`.

**State.** Sort, filters, search, page and page size each work controlled (`sort` + `onSortChange`, `filters` + `onFiltersChange`, `search` + `onSearchChange`) or uncontrolled (`defaultSort`, `defaultFilters`, `defaultSearch`). A new sort, filter, search or page size goes back to page 1. Keep the query in the URL or a store (`createStore`) to restore a view.

**Labels.** `labels` translates every text, including the range (“1–10 of 245”) and the sort description; `locale` sets text sorting and number formatting.

## Accessibility

- It is a native `<table>` with a caption; the table scrolls inside a focusable region named by the caption.
- Sortable headers are buttons: Enter or Space sorts, Shift+click adds a secondary sort. The primary sorted column has `aria-sort`; every sorted header's button is described as “sorted ascending/descending” (with its priority when several columns sort).
- The range (“11–20 of 245”) and “Loading…” are in a status region, so page changes and loading are announced politely. Errors are announced with `role="alert"`.
- The rows-per-page select and the pagination are labelled; translate them with `labels`.
- The search field is a labelled `searchbox`. Each filter button is named “Filter Name”, and “Filter Name (active)” while the column is filtered; it opens a dialog named like it, with labelled fields, that returns focus to the button on close. Active filters are a named list; each remove button names the filter it removes.
- Each row checkbox is named after the row (“Select Ayşe Kaya”); the header checkbox selects the page and is announced as mixed when only some rows are. Selected rows are marked by colour and by the checked box.
- The bulk bar is a group named “Bulk actions”; its count is a status region, so “3 selected” and “All 245 results selected” are announced. When the bar disappears, focus moves to the header checkbox; after “Select all results”, focus moves to “Clear selection”.
- The row menu button is named “Actions for Ayşe Kaya”; the menu has roving focus and typeahead. The same actions open from the keyboard with the Menu key or Shift+F10 while focus is in the row.
- The detail button is named “Details for Ayşe Kaya”, has `aria-expanded` and points to the detail row with `aria-controls`. The detail and action columns have visually hidden header names.
- A column header is named by its label alone (`aria-labelledby`), not by its filter button or resize handle.
- Each resize handle is a focusable separator named “Resize Name”, with its width in pixels as `aria-valuenow` and the limits as `aria-valuemin` / `aria-valuemax`.
- Dragging headers is pointer-only; the column chooser moves columns with buttons (“Move Name up”), keeps focus on the button and announces the new position. Its checkboxes are named after the columns; a column that cannot be hidden, and the last shown one, are disabled. Each pin select is named “Pin Name”.
- The default pin labels say “Left” and “Right”: translate them in right-to-left apps, where the start side is on the right.
- Each row's drag handle is a button named “Reorder Ayşe Kaya” and described by the keyboard instructions. Picking up, each move (“Ayşe Kaya: position 3 of 10.”), the drop and a cancel are announced in a status region; leaving the handle cancels.
- Virtualized, the table has `aria-rowcount` (all rows plus the header) and each rendered row its `aria-rowindex`, so screen readers report positions in the whole table. Spacer rows are hidden from them. Rows that are not rendered cannot be reached with Tab — use search and filters to find a row, and paging when every row must be reachable by keyboard.
- “Load more” is a real button, so loading never depends on scrolling.
- `onRowClick` is a pointer shortcut only: rows are not focusable, so keep a link or a row action that does the same.
- When filters or search leave no rows, the empty message says so and offers a button that clears them.
- Shift+click has no keyboard equivalent beyond Shift+Enter in most browsers — offer a preset view (as in the controlled example) when a multi-column order matters.

## Do / Don't

| Do                                                           | Don't                                                    |
| ------------------------------------------------------------ | -------------------------------------------------------- |
| Set `getRowId` to the record id.                             | Rely on the index when rows sort, page or get removed.   |
| Use `mode="server"` for large or remote data.                | Load 10,000 rows into the browser to sort them.          |
| Give actions columns a visible label and real buttons/links. | Make the whole row clickable as the only way to open it. |
| Keep the query in the URL for shareable views.               | Reset the user's sort on every data refresh.             |
| Add filters to the columns users actually narrow by.         | Put a filter on every column.                            |
| Confirm destructive bulk actions, then `clearSelection()`.   | Delete hundreds of rows on one click with no undo.       |
| Pair `onRowClick` with a link or a row action.               | Hide the only way to open a record behind a row click.   |
| Pin the column that identifies a row (name, number).         | Pin so many columns that nothing is left to scroll.      |
| Give `storageKey` a name unique to the screen.               | Share one key between tables with different columns.     |
| Save the new order in `onRowReorder`, then update `data`.    | Offer reordering on a sorted view.                       |
| Virtualize long lists without paging; keep search at hand.   | Virtualize a 20-row page.                                |
